### Era set — fantasy → modern → future, in matched light/dark pairs

| Theme | Mode | Colors | Vibe |
|---|---|---|---|
| [Runeforge Light](runeforge/runeforge-light-v1.0.json) · [Dark](runeforge/runeforge-dark-v1.0.json) | both | 8 | **Fantasy.** Illuminated manuscript by day, forge-lit vault by night — heraldic jewels over limestone or warm charcoal. |
| [Meridian Light](meridian/meridian-light-v1.0.json) · [Dark](meridian/meridian-dark-v1.0.json) | both | 8 | **Modern.** Contemporary product-design flat UI — cool neutrals, one confident indigo lead, colour used sparingly. |
| [Hyperion Light](hyperion/hyperion-light-v1.0.json) · [Dark](hyperion/hyperion-dark-v1.0.json) | both | 8 | **Future.** Near-future instrument panel — graphite and glass, electric cyan lead, high chroma on a short leash. |

Generated by [`_build-era-themes.py`](_build-era-themes.py). Two things separate this set from
the others in the library:

**Light and dark are twins, not cousins.** A family declares its hue angles once and both modes
are derived from them, so `dataColors[i]` means the same thing in either. A report can switch
mode without re-authoring a single conditional format. The two luminance ladders deliberately
run in *opposite* directions — prominence is contrast against the surface, so on white the lead
series is the darkest and on charcoal it is the lightest.

**The luminance ladder is solved, not picked.** Greyscale separation is the constraint hand-
mixing always loses: invisible on screen, obvious on a mono printout. The generator takes a
target relative luminance per slot and binary-searches HSL lightness (shedding chroma only when
a hue cannot reach the target) until it hits it, so the ladder is right by construction.

Three gates, all measured, all fatal to the build: **WCAG** (4.5:1 text, 3:1 fills, against both
surfaces), **greyscale** (≥1.25:1 between the leading four), and **CVD** (≥0.18 pairwise under
simulated deuteranopia *and* protanopia, Viénot 1999). The gated four follow Okabe-Ito's shape —
blue, gold/amber, a bluish-green and a reddish-purple. Reds and true greens live at slots 4–7 on
purpose: a red, a green and an orange in the same gated set collapse under both CVD conditions.
They remain available as the semantic `good` / `bad` keys, where they are read one at a time
rather than compared side by side.

**Pick:** general-purpose light or dark → Meridian · dark dashboard with presence → Hyperion Dark ·
narrative or game/lore data → Runeforge · widest CVD margin → Meridian Light (0.236) or Hyperion
Dark (0.297). Each folder's `notes.md` carries the full palette and its measured margins.

Apply: see [Applying to a report](#applying-to-a-report) below.

## Convention

```text
projects/themes/
├── README.md
└── <theme-slug>/                   ← one folder per theme family
    ├── brief.md                    ← OPTIONAL — design intake (read FIRST by the agent)
    ├── <theme-slug>-v1.0.json      ← built monolith — source of truth, distribute this
    ├── <theme-slug>-v1.0.Theme/    ← OPTIONAL — serialized fragments for editing
    │   ├── _config.json
    │   ├── _wildcards.json
    │   ├── textbox.json
    │   └── …
    ├── notes.md                    ← OPTIONAL — design rationale, change log
    └── preview.png                 ← OPTIONAL — screenshot of the theme on a report
```

`brief.md` is the **intake** (decisions to drive authoring); `notes.md` is the **rationale** (why we ended up here). Both optional; either or both is fine.

`<theme-slug>` is kebab-case. Version goes in the **filename**, not in folder names — keeps the folder stable while versions iterate.

## Why themes get their own home

A theme is a self-contained artifact that may apply to many reports. Storing it inside a single `.Report/StaticResources/RegisteredResources/` couples it to that one report. Storing it here means:

- One source of truth, distributed via `pbir theme apply-template` or `apply/file.md`
- Iterate the theme without touching consumer reports
- Diff between versions with `pbir theme diff`
- Register as a CLI template for the whole machine (`~/.pbir/templates/themes/`)

## Workflow

### Authoring a new theme

See [`../../02-build/theme/create/_index.md`](../../02-build/theme/create/_index.md) for the 7-step authoring workflow. Drop a `brief.md` at `projects/themes/<slug>/brief.md` first if you have specific decisions to capture (template: [`../../02-build/theme/create/brief-template.md`](../../02-build/theme/create/brief-template.md)).

Land the result here:

```bash
mkdir projects/themes/<slug>
pbir theme serialize <base>.json -o projects/themes/<slug>/<slug>-v1.0.Theme
# edit fragments
pbir theme build projects/themes/<slug>/<slug>-v1.0.Theme -o projects/themes/<slug>/<slug>-v1.0.json
```

### Applying to a report

Round-trip the monolith through the serializer — this writes the theme into the report's
`RegisteredResources/` and repoints `report.json` at it:

```bash
pbir theme serialize projects/themes/<slug>/<slug>-v1.0.json -o /tmp/<slug>.Theme
pbir theme build /tmp/<slug>.Theme -o "<report>.Report" -f --clean
pbir theme validate "<report>.Report"
```

> `pbir theme apply-template` takes a **registered template name**, not a file path — there is no
> `--from-file` flag (verified against pbir 0.9.25).

Or register once, apply many times: [`../../02-build/theme/apply/share-as-template.md`](../../02-build/theme/apply/share-as-template.md).

### Versioning

Bump the version in the **filename** when you change anything that consumer reports would see:

- `<slug>-v1.0.json` → `<slug>-v1.1.json` for tweaks (color shift, font size)
- `<slug>-v1.x` → `<slug>-v2.0.json` for breaking changes (palette rework, structural overhaul)

Keep old versions in the folder so consumer reports pinned to an old version still work.

## Rules

- **Distribute the built monolith**, not the `.Theme/` folder. Consumers apply `<slug>-vX.Y.json`.
- **Do not put a `.Theme/` folder inside a `.Report/`** — PBIR hooks reject fragments. See [`../../02-build/theme/where-themes-live.md`](../../02-build/theme/where-themes-live.md).
- **Validate before committing**: `pbir theme validate projects/themes/<slug>/<slug>-vX.Y.json`.
- **UTF-8 without BOM** for every JSON file.
